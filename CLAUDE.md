# Melodic Studio

Cross-platform desktop developer workspace: a git client in the spirit of GitHub Desktop, a read-mostly code viewer, and AI agents that each work in their own git worktree. Tauri 2 + Melodic JS/Components 4. Started 2026-11-16 as "Repoman" (the folder still carries that name; components are `ms-*`, app tokens `--ms-*`). Layout and conventions follow `../chamber`.

## Decisions (do not regress)

- All git work shells out to the user's `git`, so SSH agent, credential helpers, hooks and signing just work. No stored tokens, and the app itself calls no host API. Web links (issues, pull requests, commits) are built from the remote URL and opened in the browser.
- Host data (issues, work items, pull requests, new repositories) comes only through the command-line tool the user has signed in to: `gh`, `az` with the azure-devops extension, `glab` (`host_cli.rs`). When the tool is missing or signed out the UI says exactly what to install or run and falls back to the web page. Arguments are separate argv entries in `--flag=value` form (never a shell line); long text goes on stdin (`gh --body-file=-`) or through a temp file (`az --flag=@file`, which also keeps `az.cmd` quoting out of it); names starting with `-` or `@` are refused. Nothing is installed for the user (`AZURE_EXTENSION_USE_DYNAMIC_INSTALL=no`).
- Text from the host (issue bodies, titles, labels) is untrusted: shown as plain text only (work item HTML is reduced to text in Rust), never as HTML. In an agent's task it is fenced and labelled as a description, and the user edits the task before starting.
- Publishing happens only on an explicit click: `pr_create` from the Create button of the pull request dialog (which refuses until the branch is fully pushed), `host_repo_create` from the new-repository flow; reviews, comments, merges, new issues, issue state changes, CI re-runs and Jira moves (`host_ops.rs`) each from their own button. Never as a side effect of anything else. Jira goes through Atlassian's `acli` only (no token kept); its site and project per repository are in localStorage `studio.jira`. `host_open` opens only https pages on the repository's own host.
- `GIT_LITERAL_PATHSPECS=1` on every call so file names are never read as globs. `git stash` breaks under it; those calls use `run_magic`.
- Commit model is GitHub Desktop's: the checked files are the commit. `commit()` resets the index (except mid-merge), adds exactly the selected paths via `--pathspec-from-file`, then commits.
- History operations (`git.rs`, `ms-git-ops`): cherry-pick takes several commits, oldest first, in one `git cherry-pick`. Squash merge is `merge --squash` then a commit with the dialog's message on stdin; on conflicts the message is written to SQUASH_MSG and the operation shows as `squash` (only while files are conflicted: SQUASH_MSG outlives a squash finished in a terminal), Continue commits from it, Abort is `reset --merge`. Interactive rebase is git's own `rebase -i --autostash` with `GIT_SEQUENCE_EDITOR` set to `cp '<our todo file>'` (git starts the editor through its shell; Git for Windows brings one); the todo and new messages live in `<git dir>/studio-rebase/`, and a new message is an `exec git commit --amend --no-verify -F <file>` after the commit's last squash/fixup, so a stop for conflicts in between keeps it. The list sent must be exactly the commits of `upstream..HEAD` (re-read in Rust), merges in the range are refused, and the first kept line cannot be squash/fixup. Rows are reordered with pointer events, not HTML drag and drop (the window's file-drop handling).
- Deleting a local branch can delete it on the remote too (a box in the dialog, unticked). What that deletes is `Branch.published`, worked out in `Git::branches`: the remote branch of the same name, on the upstream's remote, else on the only remote that has one; never the upstream as such (a branch made from `origin/main` tracks `origin/main`). The dropdown marks such branches with a cloud. `Git::branch_delete(name, force, remote)` deletes the remote first, after checking that some other branch has the commits (`git branch -d` would accept "merged into its upstream", which is going too) and that no checkout holds the branch.
- Undo/amend are only offered while the tip commit is on no remote. Force push is `--force-with-lease`, offered only after a rejected push.
- Commit identity is git's own config, nothing stored by us: Settings edits `--global` user.name/email, and "Use a different name and email in <repo>" writes `--local` (the main checkout's `.git/config`, so its worktrees and agents share it); unticking unsets it. `identity_get` / `identity_set` in commands.rs. There is no external-editor setting: editing happens in the Files tab.
- Files tab operations (`files.rs` create / relocate / duplicate / trash / import / locate): every path through
  `resolve()` (folders) or `entry()` (the entry itself, so a symlink is moved, never its target); never replaces without
  `OnConflict` saying so; trash, with deleting only for files where there is no trash. Drops from outside use Tauri's
  `onDragDropEvent` (positions / devicePixelRatio, which includes the webview zoom); moves inside the tree use pointer events.
- Discard restores tracked files from HEAD and moves untracked ones to the OS trash.
- Branch/ref/hash arguments go through `check_ref` (nothing starting with `-`).
- Files tab (`files.rs`): paths are repo-relative and resolved through `resolve()`, which refuses absolute paths, `..`, `.git` and symlinks leading out. Saving never creates a file, and a file that changed on disk since it was read is not overwritten without asking. `Git::ignored` drops `GIT_LITERAL_PATHSPECS` because `check-ignore` rejects it.
- Find in files is `git grep --untracked -n --column -I -z` in the active checkout (`Git::grep`, command `files_search`): tracked and new files, `.gitignore` respected, binaries skipped, the text as one argument after `-e` with `-F` unless the regular-expression option is on (`-E`). The native side reads git's output as it comes and stops git at 2,000 matching lines (`truncated`); a line is cut around its match in Rust and columns are converted from git's bytes to the editor's UTF-16 units there. git does the finding; `shared/search.ts` only marks the matches in each line with a JavaScript expression made from the same text and options (nothing is marked where the two dialects differ). The state lives in `SearchStore`, not the component: the sidebar is rebuilt on every tab switch. An answer to an older search is dropped by a counter. Results are text bindings only.
- Open a file by name: the list is `git ls-files --cached --others --exclude-standard -z` (`Git::files`, command `files_list`; duplicates of a conflicted file and submodule entries are dropped in Rust, since `--deduplicate` needs git 2.31), kept per checkout in `FileIndexStore` and read again each time the box opens. Files deleted since the last commit are still in git's list, so the box drops the ones the status marks deleted. Matching is `shared/fuzzy.ts`: fzy's scoring, each typed word must match, and a word found inside the file name outranks the same letters spread over the folders. A file opened lately wins a tie and leads when nothing is typed (`ExplorerStore.open` reports to `FileIndexStore.opened`).
- Monaco is imported only through `shared/monaco.ts` (dynamic import, so startup does not pay for it). Worker imports use the package's export paths (`monaco-editor/editor/editor.worker.js?worker`), not `esm/vs/...`.
- Status is polled every 5 s while visible and on window focus; `GIT_OPTIONAL_LOCKS=0` keeps that from fighting a terminal.
- Background fetch (Rick, 2026-11-23): after a status poll, `RepoStore.fetchIfDue` fetches the repository on screen when its last fetch (FETCH_HEAD's time, so a terminal's counts) is over 5 minutes old (`FETCH_EVERY_MS`), the window is showing and nothing else is running. It sets no `busy` and says nothing, also when it fails; a failed one is tried again after 5 minutes (`_fetchTried`). A fetch, pull or push started meanwhile waits for it (`act` awaits `_quietFetch`: two gits fetching into one repository trip over ref locks). The native side is `Git::fetch_quiet` (`fetch_background`): no askpass of any kind (`GIT_ASKPASS` empty, `SSH_ASKPASS_REQUIRE=never`, `GCM_INTERACTIVE=never`) and stopped after 60 s, so it can never put a password window up; what needs an answer is asked by the fetch the user clicks. Off in Settings > General (localStorage `studio.fetch.auto`). Only the repository on screen: another tab's is fetched within a poll of being switched to.

- Worktrees: `RepoRef.worktree` is the active checkout. `commands::repo()` resolves every command to it, so Changes, History, Files and language servers follow a worktree switch with no per-command work; `main_repo()` is for the few commands that must act on the main checkout. The frontend calls `RepoStore.switchContext()` after any switch.
- Agents are Claude Code, not a reimplementation: `claude -p --output-format stream-json --verbose --permission-mode <mode> [--resume <id>]`, prompt on stdin (never argv), cwd checked against the repository's worktrees. Only assistant/user/result/init events are forwarded. `claude -p` counts as the SDK, which hides the Artifact tool, so `agent::claude()` sets `CLAUDE_CODE_ARTIFACT=1` unless the user set it (their `enableArtifact: false` still wins). `total_cost_usd` is the session's running total. Open-ended agents do not commit; the user reviews in the Changes tab of the agent's worktree, commits, then merges. Pipeline tasks (below) are committed and pushed on their own branch by Studio. The Merge… dialog (agent-session.component.ts) lets the user pick the target: any local branch (merged where it is checked out: its worktree, else the main checkout switches to it first and must be clean) or a new branch made from one; or, for protected branches, "Open a pull request" switches to the agent's worktree and opens the normal PR dialog. `AgentsStore.merge(session, into, from, cleanup)`: the dialog's "Then delete its worktree and the branch" box (ticked by default, remembered in localStorage `studio.agents.merge-cleanup`) removes the agent's worktree and deletes its branch (`-D`, since `-d` judges from the main checkout's HEAD) after a successful merge, unless the worktree has uncommitted changes (kept, with a toast). The session stays.
- Agent sessions have a `kind`. `task` is the above. `ask` is a read-only chat (Ask the repository, History questions): it runs in the active checkout, never a new worktree, in `default` permission mode with `RunOptions { tools, builtin, lean }`. `tools` (`ASK_TOOLS` in agents.store.ts) is the allow-list, `builtin` (`--tools`) limits the tools Claude can even see to the names in it, so the user's own settings cannot widen it; `lean` skips MCP servers and skills but keeps the session, so follow-ups `--resume`. History questions add `Bash(git log:*)`, `git show`, `git diff`, `git blame`. The first prompt (`askPrompt`) carries the rules; run against the real CLI it had to say "one plain git command, no `cd`, no `git -C`, no pipes", because those forms do not match the rules and are refused.
- Images go with a message to any session (task, question, investigation): pasted into the composer, dropped on the session pane, or picked with its Image button. `claude -p` takes one only as a content block, so a turn with images adds `--input-format stream-json` and its stdin is one line of JSON, images first, then the text, which may be empty (`agent::turn_input`; checked with 2.1.329, with `--resume`). The window makes each ready (`prepareImage`): a PNG, JPEG, GIF or WebP up to 2,000 px on its longer side and 3.7 MB goes as it is (known by its first bytes, not its name), anything else the web view can decode is drawn smaller and encoded again. Waiting images live in `AgentsStore.attached` (memory, per session). `send` saves them under names of ours in `agent-sessions/<id>.images/` and passes only the names (`RunOptions.images`, 10 at most); the native side checks name, bytes and size again and reads them from there, so a path never comes from the window. The transcript keeps the names (`AgentItem.images`) and shows them as `data:` addresses read back on demand, one session's at a time (`AgentsStore.shot`; the content policy allows no `blob:`). Drops in the app come from Tauri's `onDragDropEvent` with paths, read by `agent_image_file` (files named as images only). Every box that writes to Claude takes them the same way through `ms-attach` (`box` = a session id, or a `DRAFT_IMAGES` key while no session exists yet: the new-task dialog, a new question, Investigate a bug, an issue's task); the draft's images go with the first message (`NewTask.images`, `ask(…, images)`, `InvestigateRequest.images`, every attempt gets them) and stay in the box until the start succeeds. A paste counts when its event path passes through the zone; a Tauri drop when `hits(zone, x, y)`, so a dialog over a pane takes the drop and the pane under it does not. A Claude conversation in the workspace is Claude Code in a terminal: a paste holding an image and no text sends Claude Code its own paste-image key (Ctrl+V, Alt+V on Windows; `ScreenEvents.claude`), which reads the clipboard itself, and a file dropped on any terminal is typed in as its path (`shellPath`, escaped for the shell), which is how Claude Code takes a dropped file.
- Agent text is never HTML. `rich-text.ts` parses the Markdown itself and renders through templates; the only links are made there: `path:line` (opens the Files tab at the line via `ExplorerStore.openAt`), commit hashes in history sessions (selects the commit, loading more history until it is found) and http(s) addresses (opener plugin). File detection is strict on purpose (`fileRef`): a link that opens nothing is worse than none.
- Agent sessions are files, not browser storage: `<app data dir>/agent-sessions/<id>.json` (`history.rs`; with `STUDIO_CONFIG_DIR` set in a debug build, under that folder). `AgentsStore.sessions` is empty until `restored` resolves; `init()` waits for it. `save(sessions)` compares the new list with the old by identity and writes what differs: at once when the session is not mid-turn (a turn ended, a session was made, marked or removed, which deletes its file), otherwise within 500 ms, so a stream of events is one write per half second. One write per session at a time (async commands can overtake each other); the native side writes beside the file and renames over it. A failed write is said once ("Agent history is not being saved", said again only after a write has succeeded in between) and tried again at the next change. `pagehide` flushes what is waiting. What versions before 0.6 kept in localStorage `studio.agents` is moved over at the first start and the key removed once every session was written; the browser preview's demo backend still keeps its sessions under that key. The whole transcript is kept (the old 400-item cut is gone), and the transcript pane renders its last 300 items with "Show earlier".
- Parallel attempts are ordinary task sessions sharing a `group`, on `branch`, `branch-2`, `branch-3`. Each records `base`, the commit its worktree started at; `worktree_diff` compares the checkout with it (commits since, uncommitted and untracked work) without touching the index or the files. "Keep this one" deletes the other attempts' worktrees and branches.
- The agents store listens for events from app start (the toolbar's `ms-claude-control` calls `init()`), not from the first visit to the Agents tab, so sessions in other repositories and ones started from elsewhere (`AgentsStore.start`) stay right. A turn that ends while not on screen sets `unread` (it then counts as waiting on the user, see Fewer surfaces) and shows a toast. Every store action is a plain awaitable method; `idle(id)` resolves when a session's turn has ended.
- Language servers are whatever the user has installed (a project's `node_modules/.bin` first, then PATH); nothing is bundled or downloaded. The protocol is spoken in `lsp.service.ts`; the Rust side only frames messages. The editor component knows nothing about it.
- AI features around changes are one-shot `AiService.ask()` calls and never change the repository by themselves. What they send is bounded: `ai_git.rs` caps a diff at ~60 KB, giving every file an equal share (small files stay whole) and writing a note where something was cut. Prompts declare repository content to be data. Answers reach the page through text bindings only (`components/ai/markdown.ts`); never `unsafeHTML`.
- A new task's branch is named after what the task says. The field fills at once with `branchFor` (the words that are not filler, at most 4, 40 characters); when the task's words do not fit in that (`wantsNaming`), Claude is asked once the typing pauses for 800 ms (`branchNamePrompt`, haiku, no tools, the task fenced as data) and its answer replaces it through `namedBranch` (a-z, 0-9 and hyphens only, under `agent/`). A branch typed by hand is never replaced, an answer for an older wording is dropped, and Start does not wait for one. Without Claude the task's own words stand.
- Commit message (haiku, no tools): text the user typed is never replaced; the answer is then offered as a suggestion to take or dismiss.
- A review has a scope (`ReviewRequest`, `ai_review_diff`): `push` is merge-base(upstream, HEAD)..HEAD, or the merge-base with the default branch when the branch has no upstream; `branch` is merge-base(a branch, HEAD)..HEAD, pushed or not, which is what a pull request carries (the branch is the pull request's target, the remote's copy of it first, else the default branch); `work` is a commit to the files as they are, new files included (`worktree::diff_since`, so nothing is staged or touched): the agent's `base` in its worktree, HEAD elsewhere. The diff in the prompt has new-file line numbers written in (`numbered()`), so findings name real lines; `ms-diff` shows them in place through `.notes` (keyed by new-file line). A `work` review has no end commit (`head` is ''), so a finding's file is diffed against the working tree, and a file git does not track is read only when git itself lists that exact path as untracked (the name is Claude's). Sonnet, read-only tools (`Read`, `Grep`, `Glob`).
- Where a review starts (Rick, 2026-11-20: after a push the option was gone, and an agent's uncommitted work had none): the strip in Changes and History and the cards of "No local changes" have one button per offer of `AiFeaturesStore.offers` (`shared/review-offers.ts`: "5 uncommitted", "2 to push", "vs main"; in an agent's worktree "Agent's work" stands for all of it, since never pushed its "to push" and its branch are the same diff); "Review with Claude" in a session's header goes to its checkout first (`reviewSession`); "Review with Claude" on a pull request in the Pull requests dialog checks it out in its worktree and compares with its target. Nothing of a review is posted to the host. `review()` calls `settle()` before it starts: the effect that drops another checkout's results runs after a switch, and would otherwise take the review just started for an old one.
- Conflict proposals: Claude answers one replacement per conflict block and the frontend splices them into the file, so nothing outside a block can change (and a long file costs no more than its conflicts). ## The project's own formatter

Step 8 of `docs/daily-driver.md`.

- A file is formatted by its project's Prettier when the project brings one: a `node_modules/prettier` in the file's folder or one above it, up to the checkout, and a Prettier config that applies to the file (any of Prettier's own file names, or a `prettier` key in package.json), looked for the same way and never above the checkout (`format.rs`, `prettier_for`). Installed without a config does not count: such a project is formatted as before. Nothing is installed for the user and nothing global is used.

"No parser could be inferred" means the file is not Prettier's to format (`None`); any other failure is said in its words (a toast, not repeated for the same file within 30 s) and nothing else formats in its place.
- Monaco formats with one provider: the best match for the file, and among equals the one registered last. `FormatterService` gives each file of such a project a provider of its own, by its exact path (`{ scheme, pattern: fsPath }`, which scores as a language does), and registers it again when the file is shown, two seconds after it opens (a language's own formatter can register late), on window focus, and right before a format on save (`ready`). A file Prettier does not know is handed on to `LspService.format` (a `.rs` in a project with Prettier goes to rust-analyzer). Only whole-file formatting: Format Selection stays with the language server.
- The same shape fits `ruff format` and `black`: a finder like `prettier_for` and the same call.

## Task pipeline

Rick, 2026-11-21 (mock-up: claude.ai/artifact/SxYXPkshnWVFCh4G7tWRAi): a dead simple view of work that gets planned, coded, reviewed, tested and fixed without babysitting.

- A task of a kind of work (Quick fix, Bug, Feature, Chore; "Open-ended" is the old agent session) runs Plan → Code → Review → Test → Fix → Ship (`shared/pipeline.ts`, `AgentSession.pipeline`), always in a worktree of its own. Code, Review, Test and Fix loop until the review has nothing that blocks (`bug`/`risk`; nits do not) and every test passes. After 3 fixes (`MAX_FIXES`) it stops and asks: One more round, Take over, Mark done. The user is asked twice in a normal run: approve the plan (a Bug or Feature; a Chore approves itself, a Quick fix has no plan or review) and ship.
- Claude's steps are turns of the task's own session: the plan with `PLAN_TOOLS` only (read and search, `--tools` limited too), code and fixes in `acceptEdits`, each with its own model (`Pipeline.models`, picked in the step's detail; defaults Sonnet, review Haiku). The prompts (`pipeline*Prompt` in ai-prompts.ts) tell Claude not to commit, push or run the test suite.
- Studio's steps: after Code and each Fix it commits everything in the worktree as the user, message from the brief, and pushes the branch (`pipeline_commit`; a failed push is said, not fatal). Review is `AiService.ask` with `where` set to the worktree, over `pipeline_review_diff` (everything since `base`). Test runs the project's test targets (`targets.rs`, at most 4) in the worktree with `CI=true`, 20-minute limit, output tail kept (`pipeline_test_run`, stoppable); no test targets counts as passing.
- Budgets are not enforced (Rick: cost is shown per step and per task, he steps in by hand). Each Claude step's cost is the session's total minus `Pipeline.mark`; reviews add their own.
- Cleanup: once the work lands (merged from the Merge dialog, or `Worktree.landed` seen by `settleReviews`) and when the task is discarded, `pipeline_clean` removes the worktree, deletes the branch with `-D` and its pushed copy on every remote (never the main checkout's branch or a remote's default). The session stays as a record. The hooks into `AgentsStore` (`turnEnded`, `landed`) are maps keyed by name, so a reloaded module replaces its listener.
- A step that was going when the app closed waits for "Carry on" (`reviveDuring`). Messages typed in the session's box go to the step: changes to the plan while it waits, otherwise more work that is committed and checked again.
- The desk and the Agents page have List / Board (localStorage `studio.agents.view`); the board has seven columns, Plan to Done (today's).

- A bug blocks always; a risk only before the first fix (`blocking(findings, fixes)`), then it is listed at Ship. The review is given the task's own words (`pipelineReviewNote`) and told not to report what was asked for. Both came from the first real run, which otherwise looped to the fix limit with every test green.
- Every review first commits whatever is in the worktree (`PipelineStore.commit`), so work a stopped step left uncommitted is never missed by a merge.

Run for real (2026-11-21, desktop window by script, Claude Code 2.1.330, a scratch Node project with a bare remote): a Bug task planned read-only ($0.26), approved, coded, committed and pushed, reviewed, tested with `node --test`, fixed, re-checked, merged into main, and its worktree, branch and pushed branch deleted; main's tests passed. About $1.25 in all. Also checked in the browser preview: Quick fix to Ship by itself, the fix limit, Discard, the board. Not run for real: a Feature with a question, other test runners, Discard, the board in the window.

- The Run control (`ms-run-control`, right side of the toolbar) is hidden while `RunStore.targets` is null or empty, by a `hidden` attribute on its host, and carries the divider after it so both go together. `RunStore.load` looks again when the checkout or its branch changes, when the list is opened, and on window focus while the control is hidden (a hidden control cannot be opened to look again); `_seen` keeps each checkout's last list so switching repository tabs does not blink. - Ports: the main checkout keeps the app's own port; a worktree gets a free one, chosen once and remembered. .NET gets `ASPNETCORE_URLS` and `Kestrel__Endpoints__Http__Url`: a launch profile's `applicationUrl` replaces the first (found by running it), and Kestrel's endpoint setting replaces that. - PHP targets (Rick, 2026-11-23: php.melodic.dev had no Run control): a folder with a `composer.json`, or the checkout itself with an `index.php`, gives `php -S 127.0.0.1:8000 -t public` when it has a `public/index.php` (else `php -S` in the folder when it has an `index.php`; `php artisan serve` instead of either for Laravel), one target per composer script as `composer run-script --timeout=0 <name>` (Composer stops a script after five minutes by itself; its own events such as `post-install-cmd` are not offered), and `php vendor/bin/phpunit` where there is a `phpunit.xml` and no `test` script. - Compose targets (`compose.rs`, the start of Part 3 of `docs/debugging.md`): the compose file `docker compose` itself would pick in a folder gives one target per service, `docker compose up --build <service>`, and "All services" when there are several. The service names are read by a small scanner of the block form (no YAML library, nothing run to list targets). In the main checkout that is the whole command, so the user's override file and `.env` apply. A worktree's copy gets `-p <repository>-<worktree>[-<folder>]`, their files named with `-f`, and a file of ours after them (app cache dir, `compose/<project>.yaml`) that replaces every published port (`!override`, Compose 2.24.4 or later) with a free one, remembered like the others; the ports come from `docker compose config --format json`, so nothing of YAML is worked out here. `RunStarted.port` is the service's first.
- Stopping a compose target: `docker compose up` stops its containers on Ctrl+C, and compose 5 also on a hangup, but older ones and Windows (terminated) leave them running. So such a run has a `docker compose … stop [service]` that the terminal runs when it is cut off (`terminal::on_close`: tab closed, Stop, window destroyed, and `RunEvent::Exit`, since Cmd+Q destroys no window first), not when it ends by itself. `prepare` closes a copy of the same target that is still running and waits for stops under way (`Stops::settle`) before `up`: Restart's `term_close` can arrive after its `target_run`, and an `up` that attaches to containers being stopped ends with them.
- Not built of Part 3: Envy host names, the recording inside a container (an investigation of a compose target gets no recording helper, `recordingRuntime`; neither does PHP, which has none), error spotting for PHP's own messages (a non-zero exit is still spotted).
- Error spotting reads the pty's output as text (`ScreenEvents.output`). Blocks: .NET `fail:` entries with an exception and `Unhandled exception`, Node `Error:` + `at` lines, Python tracebacks (chained ones are one error), Rust panics, Go panics, failed tests (dotnet test, jest, vitest, cargo test, pytest), and a non-zero exit code that nothing else explains. An error-level log line with no stack is not an error. The "Error spotted" bar sits between the tabs and the terminal, not inside xterm.
- An investigation is an agent session of `kind: 'investigate'` (`AgentSession.investigation`) in a worktree on `investigate/<what>`, started from the commit on screen. It runs `claude -p --restricted --strict-mcp-config --mcp-config <file> --disable-slash-commands` (checked with 2.1.327): `--restricted` drops the user's own settings, so their Bash allow-rules cannot widen it, and `INVESTIGATE_RULES` (build commands only) are all the Bash it has. `agent_start` refuses an investigation in the main checkout.
- Running the app, sending it a request and running tests go only through the MCP tools (`run_target`, `http_request`, `run_tests`; also `progress`, `target_output`, `remove_recording_file`, `stop_target`). A tool that runs something emits `investigate-approval` and blocks until the window answers: `investigate_start` (the program starts on a pty the window shows as an `investigation` tab) or `investigate_answer`. "Always allow for <target>" is localStorage `studio.investigate.allow` and only makes the window answer by itself. The turn ending (`investigate::turn_ended`) stops the app and cancels what is waiting. `MCP_TOOL_TIMEOUT` is raised for these sessions, since a tool waits as long as the user does.
- Recording: every line Claude adds ends with the marker `studio-replay`; the helper appends JSON lines to `STUDIO_REPLAY_FILE` (`<worktree>/.studio/replay/run-<n>.jsonl`, `.studio/` in `info/exclude`). A step's number is its line in that file and depth comes from the enter/return events, both worked out in `replay.ts`: one helper per project cannot keep a shared counter. When a run starts, every file holding the marker is copied to `run-<n>.files/`; Replay shows those copies without their marker lines. A recording line maps to the line of code above it, a "return" to the line below.
- Cleanup: when a turn ends, `AgentsStore.conclude` checks the worktree's diff against `base` for added marker lines and helper files (`leftoverRecording`). If any remain the session is sent back to remove them (twice at most); the fix is not offered while any are left, and `investigate_commit` refuses on the native side too.
- The report is Claude's last message as JSON (`parseInvestigation`); the fix is the worktree's diff. Accept fix = commit in the worktree as the user (`investigate_commit`, the user's message, no trailer) then the ordinary Merge dialog. Discard removes worktree and branch.
- Program output, recorded values and Claude's `touches` sentence are untrusted: text bindings only. Claude's notes, thinking and evidence go through `rich-text.ts`.

## Integrated terminal

```
src-tauri/src/terminal.rs          shells on a pseudo-terminal (portable-pty: Unix ptys, Windows ConPTY): term_open / term_write /
                                   term_resize / term_close, `term-data` and `term-exit` events
src/services/terminal.store.ts     the panel's shells (per repository; screens in ScreenPool), open/closed state and height (studio.terminal.*)
src/shared/xterm.ts                lazy xterm.js load, its CSS adopted into the shadow root, theme from --ml-*/--ms-* tokens
src/components/terminal            ms-terminal: the panel under the main pane (tabs, top edge to drag, Ctrl+` / Ctrl+Shift+`)
src/services/demo-terminal.ts      the pretend shell of the browser preview
```

- The shell is the user's own: `$SHELL -l` on Unix (a login shell, because a GUI-launched app has almost no environment), `pwsh.exe`, else `powershell.exe`, else `%COMSPEC%` on Windows. It starts in the active checkout (`commands::repo`), so a new terminal follows a worktree switch; terminals already open stay where they are.
- Output travels as base64 of the raw bytes (a read can end inside a UTF-8 character) and can arrive before `term_open` has returned the key, so the store holds early events until it knows the key. Keystrokes are sent one write at a time: async commands may otherwise overtake each other.
- The xterm `Terminal` objects live in `ScreenPool`, not in a component: the work area is rebuilt on a repository or worktree switch and the panel is hidden with `display: none`, and neither may cost a shell or its scrollback. `term.open()` runs only once its element is on screen (xterm measures glyphs).
- The end of a shell comes from a thread waiting on the child, not from the output stream: ConPTY never reports end of stream. Closing a terminal hangs up (SIGHUP) on Unix and terminates on Windows; dropping the pty takes the rest along, and the window's `Destroyed` event closes them all.
- Ctrl+` is Ctrl on every OS and is caught in the capture phase, or a focused terminal would send it to the shell. Off the Mac, copy and paste are Ctrl+Shift+C / Ctrl+Shift+V; Windows also gets Ctrl+V and Ctrl+C-with-a-selection.
- Language servers: a project's own copy (`node_modules/.bin`) first, then the app's managed copy, then PATH. Nothing is bundled; managed copies are installed on request (Settings) into the app's data dir (`app_data_dir()/language-servers`: `node/` is an npm prefix, `dotnet/` a tool path, `storage/` server caches), never globally. The protocol is spoken in `lsp.service.ts` + `lsp/protocol.ts`; the Rust side only frames messages. The editor component knows nothing about it.
- TypeScript's managed install is `typescript-language-server` + `typescript@6`, not `typescript` latest: TypeScript 7 (the native compiler) ships no `tsserver.js`, which that server drives. `lsp_start` hands the client `initializationOptions` (tsserver path: the project's if it has a `tsserver.js`, else the managed one; intelephense storage paths). `.tsx`/`.jsx` go to the server as `typescriptreact`/`javascriptreact`. npm servers are started as `node <script>`, not through the `.bin` shim (a `.cmd` on Windows, where killing it would leave the server running).
- A server process has a unique key (`program@root#n`). One that exits by itself, or refuses `initialize`, is reported once (`lsp-closed` carries its last error line; `LspService.failures`, a toast, the Settings row) and not started again until `LspService.refresh()` (Restart, or any install/removal). `lsp_servers` runs each found copy with its version flag, because a file on PATH can be a stand-in that does not run (rustup's `rust-analyzer` proxy).
- Monaco never stops its TypeScript worker, which holds about 160 MB from the first TS/JS file (measured, `docs/daily-driver.md` step 5). `shared/monaco.ts` stops it (`takeDownBuiltIn`: our providers first, then the worker) when a language server takes over, and when no TS/JS file has been in an editor for two minutes (`REST_AFTER_MS`, `_resting`); showing one registers the providers again and the worker starts by itself. The only way to stop the worker from outside is a change of the language's settings, so `_stopWorkers` sets the compiler options to what they are. Built-in checks are syntax only (`noSemanticValidation`), so a test of them needs a syntax error.
- Monaco's own TypeScript/JavaScript completion, signature help, hover, highlights, definition, references, outline and diagnostics are off while a TypeScript server answers for the checkout on screen, on otherwise (`setBuiltInTypeScript` in `shared/monaco.ts`). Monaco 0.57 reads `setModeConfiguration` only once, when the first TS/JS file opens, so those eight are switched off there before any file is open and registered by us from Monaco's own adapter classes (`monaco-editor/languages/features/typescript/tsMode.js`, typed in `shared/monaco-ts-mode.d.ts`); check that import when upgrading Monaco. Monaco's diagnostics adapter writes the result of a check that was in flight when it was disposed, so while the built-ins are off any `typescript`/`javascript` markers are cleared as they appear (`onDidChangeMarkers`); without that a cold start leaves a second copy of an error that never goes away.
- What the editor gets from a language server (`lsp.service.ts`, conversions in `lsp/protocol.ts`, declared in `lsp/capabilities.json`): completion with resolve (documentation, the import a suggestion adds), signature help, hover, highlights, declaration / definition / type definition / implementation, references, outline, format document and selection, rename, quick fixes and refactorings, inlay hints, colours by meaning, code lenses, diagnostics, and a symbol search across the checkout (the `@` half of `ms-go-to`: Cmd/Ctrl+T). When that half opens, `LspService.cover` starts the server of every language the checkout has files of (from `FileIndexStore`'s list) and shows each one file of its language, because typescript-language-server only knows a project once a file of it is open; the box says what it searches ("Searches TypeScript and Rust") and which languages have no server, and `uncover` closes those files again when the box does. An empty answer in the first 12 s is asked again, since a server that has just started has not read the project yet. A feature is only asked of a server that offers it. Left out on purpose: formatting as you type, call hierarchy.
- Colours by meaning (semantic tokens; Rick, 2026-11-23: he had them in VS Code). The editor's legend is ours and fixed (`TOKEN_TYPES`, `TOKEN_MODIFIERS` in `lsp/protocol.ts`), because Monaco reads one legend per provider and every server has its own: `tokenMap` reads a server's legend against it once, and `semanticTokens` renumbers each answer (`textDocument/semanticTokens/full` only, no delta or range). Kinds a grammar already colours (keywords, strings, numbers, comments, operators) are not in the legend, so those tokens are dropped and the grammar's colour stays; dropping moves the tokens after it, which is why every position is written again. The editor's names for the kinds carry a prefix (`semanticName`: `sem.function`), so the theme's rule for one (`MEANING` in `shared/monaco.ts`, VS Code's Dark+ / Light+ colours) is never taken by a grammar token called `function` or `namespace`. Monaco's standalone theme looks a token up as `type.modifier…` from the left, so only `readonly` is a modifier of ours (rust-analyzer's `constant` counts as it). It needs the editor option `'semanticHighlighting.enabled': true`: the default asks the theme, and a standalone theme always says no. Off in Settings > Editor ("Colour names by what they are").
- Code lens ("3 references" above a type or function; same day). Lenses are listed unresolved and resolved as they come into view (`LspService.lenses` / `resolveLens`; the server's own lens is kept in a WeakMap, since `codeLens/resolve` wants it back whole). Servers name "show these places" three ways and `lensCommand` reads all three: typescript-language-server `editor.action.showReferences` and rust-analyzer `rust-analyzer.showReferences`, both (uri, position, locations), which become Monaco's own `editor.action.showReferences`; csharp-ls `textDocument/references` with the request's parameters, which becomes a command of ours that puts the cursor there and runs Peek References. Any other command is run (`workspace/executeCommand`) only when the server listed it as its own; otherwise the lens is its words and no link. typescript-language-server has its lenses off until told (`CONFIGURED`: `workspace/didChangeConfiguration` once after `initialized`, references and implementations on, functions that are not exported get none as in VS Code). rust-analyzer shows "N references" on types, traits and functions through `OPTIONS.rust`, and only makes them clickable for a client that declares `experimental.commands` (`clientCapabilities`); its Run and Debug lenses are switched off, because they hand the client a command line to start and nothing in the window starts one. A refresh from the server (`workspace/semanticTokens/refresh`, `workspace/codeLens/refresh`) and the moments inlay hints are asked for again make the editor ask again for both. Off in Settings > Editor ("Code lens").
- Rename and quick fixes are edits a server asks for across files, and Monaco only applies edits to files it has open. So they go through `LspService.applyEdit` instead (what Monaco gets back is empty): everything is checked first and nothing is changed unless all of it can be; a file open in the editor is edited there (one undo step) and saved if it had no unsaved edits before, any other file is rewritten on disk through `write_file`. The result is in Changes, where an edit across files is reviewed. An edit may also create, rename and delete files (`documentChanges` with `resourceOperations` is offered; rust-analyzer's "Extract module to file" needs it and is not even listed without). `workspaceEdit` turns the edit into steps in the server's order, and `planEdit` (pure, tested) checks all of them against the files as they are before anything is touched: nothing is replaced unless the server said overwrite, a file with unsaved edits is never renamed, replaced or deleted, and one step that cannot be done stops them all. The steps then go through the Files tab's own code (`createEntry`, `ExplorerStore.move` and `trash`, so tabs follow and a deleted file is in the trash), missing folders are made first, and a toast says what came, moved or went. typescript-language-server does not use any of this for "Move to a new file": it makes the file itself and sends plain edits, which is why the Files tree is read again after any edit that wrote a file. A quick fix reaches it through the editor command `melodic.lsp.applyAction`; a refactoring the server works out itself comes back as `workspace/applyEdit`, answered by the same code (`Client.handler`). `disabledSupport` is not declared: with it typescript-language-server lists every refactoring it knows, greyed out. The code action provider is registered with `providedCodeActionKinds` (`ACTION_KINDS`): Monaco keeps Auto Fix, Refactor, Source Action, Organize Imports and Fix All switched off until a provider names the kinds it has, which is why the auto-fix shortcut did nothing. A server that answers for a language but does not rename says so at the cursor (`noRename`); intelephense is the known one (`RENAME_NOTES`: without a licence key it answers `renameProvider: false`, checked against 1.18.5).
- TypeScript is started with `preferences.providePrefixAndSuffixTextForRename: false` (`OPTIONS` in protocol.ts): its default renames a function at a call site by aliasing the import (`greet as welcome`) and leaves the function alone.
- The editor asks for inlay hints as a file is shown, before a server has read the project, so it is told to ask again (`onDidChangeInlayHints`) when a server comes up, finishes reported work, or sends `workspace/inlayHint/refresh`.
- A repository that is no longer open in any tab (closed, replaced, removed) has its servers stopped at once (`LspService.tabsSeen`). A checkout that goes off screen has its editor models disposed (`ExplorerStore.rest`; a file with unsaved edits keeps its); the tabs, texts and scroll positions stay, and the models are made again on return. Terminals keep 5,000 lines of scrollback (`SCROLLBACK` in screens.ts): every line is held at the terminal's full width.
- A server whose checkout has been off screen for `IDLE_MS` (ten minutes) is stopped (`stopIdle`), and started again when the checkout is shown (`shown` hands its open files to `opened`). Before this every repository visited kept its servers until the app quit.
- `Client` sends one message at a time, in order: Tauri's async commands can overtake each other, and edits go to the server as ranges (`syncKind` 2), so one out of order would corrupt its copy of the file. A request takes Monaco's cancellation token and sends `$/cancelRequest`. A save is `textDocument/didSave` when the server wants it (`ExplorerStore.afterSave`): rust-analyzer only runs `cargo check`, and so only reports type errors, then. `$/progress` becomes `LspService.working`, shown by `ms-lsp-status` in the editor's header ("Rust: Indexing 42%").
- Monaco wants completion trigger characters when the provider is registered, before any server has said its own, so `COMPLETION_TRIGGERS` is every server's and `complete()` drops the characters that are not the answering server's. A completion's own command is run only when it is one of the editor's (`editor.action.triggerSuggest`, `triggerParameterHints`); a server's command is not.
- A task's change is put to the language servers when its turn ends (`AgentsStore.checkWork` -> `LspService.check`), in the agent's own checkout (`lsp_start` takes a `cwd`, `worktree_read` reads a file there, from disk or as it was at a commit; both refuse a folder that is not one of the repository's checkouts). The server is first shown the changed files as they were at `base`, which with the rest on disk is the project as it was; then they are swapped for what is on disk now and the errors read. Only when there are some are the files swapped back, to see which were there before (a change with no errors used to pay for three waits and now pays for one: about 2 s instead of 7 on a small TypeScript project, 5.5 s when a caller breaks). Errors reported for the files as they are and not for the files as they were (`newSince`: same file, same message, same line of code, wherever it moved) are the change's own. Ones that were already there, and ones the checkout causes (no `node_modules` in a new worktree), cancel out and are only counted (`known`). In between, the symbols on the changed lines (`oldSpans` + `symbolsAt`: an inserted line counts for the symbol that holds it, not for its neighbour) are asked for their references, and the files those are in are opened too, so a caller the agent did not touch is checked and listed (`impact`, "It changed greet, used in 4 places it did not touch"). Everything opened is closed again and a server started only for the check is stopped.
- A server never says it is done. A step of the check ends when every file was reported on and the server was quiet for `SETTLED_MS`, or, since a server does not report again on a file with nothing new to say, when it has answered a request sent behind the edits and stayed quiet for `UNCHANGED_MS`; never while it reports `$/progress`. It gives up after a minute without progress, five in all (`finished: false`). rust-analyzer's type errors come from `cargo check` of the files on disk (`DISK_SOURCES`), so they have no "before" and all count as new; the changed files get a `didSave` so that check runs.
- The result is `AgentSession.check`, shown above the transcript. "Ask Claude to fix them" (`fixProblems`, prompt in `ai-prompts.ts`) is the only thing that sends it to the agent. Off in Settings > Language servers (localStorage `studio.agents.check`). A changed file that is open in the editor is not swapped (its text is the editor's): its current errors are listed as they are.
- gopls, intelephense and csharp-ls learn of files changing on disk only from the client, so those three (`TOLD_OF_CHANGES`; the others watch the disk themselves and would stop if offered) are offered `workspace/didChangeWatchedFiles` and told what `LspService.statusSeen` works out: the difference between two reads of the status (`statusChanges`), everything that differs from the earlier commit when HEAD moved (`changesSince` over `worktree_diff`), and an agent's files when its turn ends. Each open document is then sent again as it is, because csharp-ls takes a new file in but only looks at an open document again when that is edited. Not seen: a file that was already modified being changed again from outside the app while it is not open.
- `csharp-ls` is pinned (`csharp-ls@0.28.0` in `lsp/servers.rs`): `dotnet tool install` refuses 0.29.0 with "DotnetToolSettings.xml was not found in the package" (SDK 10.0.300, 2026-11-19). Try the newest again before changing the pin.

## Conventions

- Melodic 3-file pattern for big components, single file for small ones. `@Service()` for DI, `@ml:click`/`@ml:input`/`@ml:change` for Melodic events, `@click` for native.
- Never import `@tauri-apps/*` at module top level; lazy-import inside `isDesktop()` checks.
- No hard-coded colors in component styles; use `--ml-*` or `--ms-*`.
- New backend command: add to `git.rs` (with a test), `commands.rs`, the handler list in `lib.rs`, `backend.service.ts` (plus a demo case), then a store action.
- A module that `npm test` imports (shared/*.ts, `ai-prompts.ts`) has no runtime imports except with a `.ts` extension from other such modules: Node runs it as it is, and cannot run decorators.
- Two kinds of front-end test, both run by `npm test`. `*.test.ts` is a pure module run by Node as it is (the rule above). `*.spec.ts` runs under vitest + happy-dom (`vitest.config.ts`): the real stores and components against the demo backend. `src/test/world.ts` gives each test a fresh app (`world()`: modules reset, storage emptied, `sent` / `on` / `emit` over the backend, toasts recorded; the demo backend's pauses are skipped), `src/test/dom.ts` mounts a component and reads it through shadow roots, `src/test/setup.ts` pins the platform to Linux (happy-dom reports the machine's own; a spec about the Mac or Windows spelling sets `navigator.platform`) and keeps Monaco from loading. Stores are imported with `await import` after `world()`. Demo turns play out on timers: `vi.useFakeTimers()` before `world()`. Monaco and xterm are mocked per spec. `npm run coverage` for the numbers. `test.fails` marks a suspected bug a test found, with the reason in a comment: fixing it means turning that into `test`.
- AI one-shots: the pull request draft is `AiService.ask` with tag `[pull-request]`, no tools, input cut to size in Rust (`pr_changes`); it must answer `{"title","body"}` and falls back to a draft from the commit subjects when Claude is unavailable.
- Commits: author as Rick only. No AI attribution trailers.

### Rules (check new code against these)

1. **Paths.** There are two kinds and they are never mixed.
   - *Repository-relative* paths (`src/app/main.ts`) are `/` separated on every OS, in both directions, exactly as git prints them. Splitting on `/` is fine. On the Rust side go through `files::resolve()` before touching disk.
   - *Absolute* paths (repository, worktree, language-server root, agent cwd) are spelled the platform's way: `C:\Users\me\repo` on Windows. Git prints `C:/Users/me/repo`, so everything git prints goes through `paths::native()` before it is stored or sent to the window (`Git::toplevel`, `worktree::entries`). A `PathBuf` built with `join()` from one of those is already native.
   - Absolute paths are never compared as strings. Rust: `paths::same(a, b)` (real-path comparison; covers `/` vs `\`, case, 8.3 short names, `/var` vs `/private/var`). TypeScript: `samePath`, `relativeTo`, `joinPath`, `fileName` from `shared/paths.ts`. No `startsWith(root + '/')`, no `split('/')`, no `` `${root}/${rel}` `` on an absolute path. Monaco's `uri.fsPath` comes back as `c:\...` (lower-case drive) on Windows, which is why.
   - `worktree_add` returns the exact string `worktree_list` reports, so the stores may match `w.path === session.cwd`. Keep it that way if either changes.
   - Paths a person typed go through `paths::typed()` (quotes from Explorer's "Copy as path", `~`).
2. **Processes.** Every process starts from `proc::command()`: it resolves bare names on PATH with PATHEXT (`claude`, `code`, `typescript-language-server` are `.cmd` shims on Windows; the extension-less file beside them is a shell script Windows cannot run) and sets `CREATE_NO_WINDOW` so no console flashes. Then:
   - Stop a child with `proc::kill_tree()`, not `child.kill()`: a `.cmd` shim is `cmd.exe` -> `node.exe`, and killing `cmd.exe` leaves node running.
   - Free-form text (a prompt, a commit message for a tool other than git) goes in on stdin, never argv: Rust refuses `.cmd` arguments that contain a line break.
   - Feed stdin from another thread while reading stdout (`git::exec` does); writing it all first deadlocks once both pipes fill, at 4 KB on Windows.
   - No shell: no `sh -c`, no `true`, `/dev/null`, `$HOME` or `&&` in a command. (`git diff --no-index -- /dev/null <path>` is fine: git itself special-cases that literal name on Windows. `GIT_EDITOR` is `:`, which git treats as "no editor" without starting anything.)
   - Something the user carries on with (editor, terminal) goes through `proc::launch()` so it is detached and reaped.
3. **Line endings.** `.gitattributes` forces LF in every checkout. Never assume the user's files are LF. Tests that compare file contents set `core.autocrlf false` in their scratch repository (Git for Windows defaults to converting).
4. **Tests.** Temp dirs are spelled differently from what git reports (`/var` vs `/private/var` on macOS, `RUNNER~1` vs `runneradmin` on Windows CI): assert with `paths::same` or `Path::ends_with`, not string equality. File names must be legal on Windows (none of `* ? " < > | :`). No Unix-only test without `#[cfg(unix)]`.
5. **Window and keys.** `titleBarStyle: Overlay` and `hiddenTitle` only exist on macOS; Windows and Linux get their normal title bar, so the toolbar reserves traffic-light room and handles dragging only when `isDesktop() && isMac()`. Shortcuts test `e.metaKey || e.ctrlKey` (Monaco: `KeyMod.CtrlCmd`) and are shown with `isMac() ? '⌘' : 'Ctrl+'`. Platform checks are `isMac()` / `isWindows()` in `backend.service.ts`; nothing else reads `navigator.platform`.
6. **Web features.** The floor is Safari 17 / Chromium 114 / WebKitGTK 2.42 (table below). Anything newer needs a fallback or a line in that table. `main.ts` shows a plain message instead of the app when the web view is older.

### Per OS

- **macOS** (WKWebView): overlay title bar with the toolbar underneath. `paths::fix_path()` matters most here: Finder-launched apps get a bare PATH.
- **Windows** (WebView2): needs Git for Windows (MSYS or Cygwin git prints `/c/...` paths, which are not handled). `fix_path` only adds Git's and npm's install folders when PATH lacks them. "Open in terminal" tries Windows Terminal (`wt -d`), then `cmd`. `build.rs` embeds `windows-app-manifest.xml` in every executable, because the unit-test binary otherwise fails to start (`STATUS_ENTRYPOINT_NOT_FOUND`: tauri-build only gives the app binary the Common Controls 6 manifest). `files::resolve` also refuses the Windows aliases of `.git` (`.git.`, `.git::$INDEX_ALLOCATION`, `GIT~1`).
- **Linux** (WebKitGTK via `webkit2gtk-4.1`): the `.deb` and `.rpm` depend on `git`; an AppImage uses whatever git is installed. "Open in terminal" tries `$TERMINAL`, the desktop's own terminal, then a list (`proc::LINUX_TERMINALS`). "Show in file manager" needs `xdg-open`. Discard uses the FreeDesktop trash and falls back to deleting when there is none.
- **Both Unix**: PATH is the login shell's (`$SHELL -l -c`, 4 s limit), then the usual system folders, then tool-manager folders (snap, linuxbrew, volta, bun, asdf, mise, every nvm/fnm node version). The shell is not started interactive, so anything set up only in `.zshrc`/`.bashrc` is found through that last list or not at all.

### Reasoned but never run

Nothing below has been executed on Windows or Linux; the first CI run and a manual pass on each are the proof. The Windows-only Rust in `proc.rs`, `paths.rs`, `git.rs` and `files.rs` was type-checked and linted for `x86_64-pc-windows-msvc`, and the Linux-only branches compiled with their `cfg` flipped, but not run.

- Windows: the whole app as a window; `build.rs` manifest embedding (and so whether `cargo test` starts at all); `.cmd` resolution for `claude`, `code` and language servers; `taskkill` tree kill; `wt`/`cmd` terminal launch; no console flashes; `/dev/null` diff of untracked files; the recycle bin; NSIS/MSI bundles and the WebView2 minimum check.
- Linux: the whole app as a window; terminal detection; `xdg-open`; trash; `.deb`/`.rpm` dependencies and the AppImage; WebKitGTK 2.42 actually having popovers on by default.
- Known gaps: repositories on UNC or `\\wsl$` paths (`cmd.exe` cannot use them as a working folder, so `.cmd` tools fail there); paths over 260 characters need `git config core.longpaths true`; removing a worktree fails on Windows while a language server or agent still has it as its working folder; whether macOS 12/13 with a Safari 17 update would work (the system WebKit is what counts, so the minimum is set to 14).
